# Подготовка в OpenCode Desktop

## Для владельца

Распакуйте пакет в текущий проект так, чтобы основной файл оказался по пути:

`docs/_handoff/POLYRA_KIMI_HANDOFF_V2/KIMI_FIX_PROMPT.txt`

Папку проекта откройте в OpenCode Desktop, выберите уже настроенную Kimi-модель
и режим, которому разрешено изменять проект (обычно Build), затем вставьте
`KIMI_START_MESSAGE.txt`. Не нужно подключать новый provider или присылать API-ключи.

В архиве нет исправленного production code. Здесь задание, profiles и исходные
материалы. Вложенный source snapshot — старый справочный снимок, не обновление проекта.

## Что главный агент проверяет до coding

1. Текущая рабочая папка действительно корень проекта; user changes сохранены.
2. Какие tools делегирования доступны именно в этой сессии, и нет ли denied policy.
3. Версия/ветка OpenCode runtime, если доступна без установки дополнительных программ.
   `opencode --version` допустим только когда этот executable реально есть.
   Отсутствие CLI в PATH не доказывает отсутствие subagents в Desktop.
4. Какой primary agent и Kimi provider/model реально активны. Не печатать auth config
   целиком: там могут быть secrets. Не менять модель разработки на добавляемую Pro.

Ссылки: S1–S4 в `OFFICIAL_SOURCES_2026-09-24.md`. Документация веток различается.
Пакет намеренно не содержит автоматически применяемого полного opencode.json.

## Установка восьми проектных профилей

Из корня проекта, если Python доступен:

```sh
python docs/_handoff/POLYRA_KIMI_HANDOFF_V2/install_opencode_agents.py --project-root .
python docs/_handoff/POLYRA_KIMI_HANDOFF_V2/install_opencode_agents.py --project-root . --apply
```

Первый вызов — preview. Второй копирует только новые
`.opencode/agents/polyra-*.md`. Существующий отличающийся файл вызывает отказ;
автоматической перезаписи нет. Идентичные профили пропускаются.
Скрипт не изменяет production files, AGENTS.md и JSON/JSONC-конфиги.

Копирование можно выполнить вручную из `opencode-overlay/.opencode/agents/`,
сохраняя скрытую папку `.opencode`. Нельзя бездумно заменять существующую папку целиком.

При необходимости lead аккуратно добавляет текст `AGENTS_APPEND.md` в существующий
AGENTS.md, не стирая его содержимое, не дублируя секцию и сохраняя прежние ограничения.
Это необязательное удобство; основной prompt сам содержит рабочие инструкции.

## После установки

Проверить, что профили реально доступны для вызова. Новые файлы не означают, что
текущая сессия уже перечитала конфигурацию. При отсутствии горячей загрузки использовать
штатный доступный coding-subagent с тем же scope; Explore/read-only агент не должен
получать задачу редактирования. Нужное действие reload/reopen описывать по установленной
версии, не выдумывать кнопку интерфейса.

Ветка документации `/docs` описывает `task` / `permission.task`; `/v2/docs` —
`subagent` / `permissions` со списком правил. Применять только актуальную для runtime
схему. Настройка «максимум 4» выполняется координатором задач; это не утверждение
о существовании одноимённого JSON-параметра.

Ни один профиль не фиксирует `model`: по документации S1/S2 модель наследуется
от вызывающего primary agent. Проверить пользовательские overrides.
Права агентов остаются под управлением окружения. Их описания НЕ ограничивают
shell технически и не заменяют реальную security policy.

При блокирующем permission запросить минимальное разрешение штатным способом;
не отключать всю защиту. Без реального child call нельзя писать «субагенты работают».
Не создавать отдельные API клиенты/агентные процессы, чтобы обойти оболочку.
